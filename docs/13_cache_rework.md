## Как работает кэширование отчётов

### Зачем вообще нужен кэш

Каждый отчёт — это несколько запросов к Bitrix24 API (задачи, таймлоги, пользователи, проекты). Это медленно — 2–5 секунд на запрос. Кэш хранит уже готовый результат в базе данных, и при следующем запросе отдаёт его мгновенно, не трогая Bitrix.

---

### Где хранится кэш

В таблице PostgreSQL `cached_report_snapshots`. Каждая строка — это один уникальный «срез» отчёта:

| Колонка | Что хранит |
|---|---|
| `report_type` | Название отчёта (`users_summary`, `projects`, `team_heatmap`, `employees_comparison`, `my_dashboard`) |
| `date_from` / `date_to` | Период отчёта |
| `user_id` / `project_id` | Дополнительный фильтр (если отчёт по конкретному пользователю/проекту) |
| `payload` | Сам результат отчёта в формате JSON. Может быть `NULL` — это значит «строка есть, но кэш ещё не заполнен» |
| `request_count` | Сколько раз запрашивали этот конкретный период |
| `last_requested_at` | Когда последний раз запрашивали |
| `is_standard` | `true` — это «стандартный» период (сегодня, неделя, месяц и т.д.), он всегда обновляется |
| `refreshed_at` | Когда кэш был последний раз обновлён |

---

### Что такое «стандартные» и «произвольные» периоды

**Стандартные периоды** — 5 фиксированных диапазонов, которые всегда актуальны:
- Сегодня
- С начала текущей недели по сегодня
- С начала текущего месяца по сегодня
- С начала текущего квартала по сегодня
- С начала текущего года по сегодня

Они помечаются `is_standard = true` и всегда обновляются фоновой задачей.

**Произвольные периоды** — любой диапазон дат, который пользователь задал вручную (например, апрель прошлого года). Они кэшируются только если их запрашивали достаточно часто (подробнее ниже).

---

### Что происходит при каждом запросе отчёта

Когда браузер запрашивает `/api/reports/users-summary?date_from=...&date_to=...`:

```
Запрос пришёл
      │
      ▼
Найти строку в кэше для этого типа + дат + фильтров
      │
      ├── Строки нет → создать строку с request_count=1, payload=NULL
      │                → посчитать отчёт из Bitrix
      │                → НЕ сохранять в кэш (порог ещё не достигнут)
      │                → вернуть результат пользователю
      │
      ├── Строка есть, но is_standard=false и request_count < 5
      │     → увеличить счётчик
      │     → посчитать отчёт из Bitrix (кэш ещё не «заработан»)
      │     → НЕ сохранять payload
      │     → вернуть результат пользователю
      │
      ├── Строка есть, request_count >= 5 (или is_standard=true)
      │   ├── payload заполнен → вернуть из кэша мгновенно ✓
      │   └── payload=NULL → посчитать из Bitrix, сохранить в кэш
      │
      └── Строка is_standard=true → всегда возвращает из кэша
```

**Порог = 5 запросов.** До достижения порога произвольный период не кэшируется — нет смысла тратить место на то, что запросили один раз случайно.

---

### Фоновое обновление (Celery Beat)

Каждые **N часов** (по умолчанию 2, настраивается через `CACHE_REFRESH_HOURS` в .env) запускается задача `refresh_all_cached_reports`. Она работает в 4 шага:

#### Шаг 1: Очистка протухших кэшей
Удаляются все не-стандартные записи, которые **не запрашивались 7 и более дней**. Смысл: если никто не смотрит отчёт за апрель 2025 — не надо тратить ресурсы на его обновление.

#### Шаг 2: Загрузка списка всех записей с payload
Из базы достаются все строки, у которых есть данные. Они сортируются: сначала стандартные, потом по убыванию `request_count` — самые популярные обновятся раньше.

#### Шаг 3: Обновление стандартных периодов
Все 5 стандартных периодов пересчитываются заново независимо от того, были ли они в кэше. Если запись отсутствует — она создаётся. Это гарантирует, что «сегодня», «эта неделя» и т.д. всегда актуальны.

#### Шаг 4: Обновление кэшированных произвольных периодов (батчами)
Все пользовательские периоды с `payload != NULL` обновляются **батчами по 10 штук параллельно**. Это не перегружает Bitrix24 API и не занимает всю память разом.

```
[самый популярный, 2й, 3й, ... 10й]  ← первый батч (параллельно)
[11й, 12й, ... 20й]                   ← второй батч
...
```

---

### Итоговая схема жизненного цикла кэша

```
Первые 1–4 запроса:
  строка в БД есть (счётчик растёт), payload=NULL, данные берутся из Bitrix

5-й запрос:
  порог достигнут → payload сохраняется в БД

6-й и далее:
  данные отдаются из БД мгновенно

Каждые 2 часа (фоновая задача):
  1. Удалить записи, не запрошенные 7 дней
  2. Обновить 5 стандартных периодов
  3. Обновить все остальные кэши батчами (самые популярные первыми)

Если запись не запрашивалась 7 дней:
  удаляется на следующей фоновой итерации
```

---

### Исключения и особенности

- **`team_heatmap` с фильтром `user_ids`** — никогда не кэшируется, т.к. это нишевый запрос с динамическим набором пользователей
- **`my_dashboard`** — кэшируется как и все, но при фоновом обновлении обрабатывается отдельно, т.к. требует `user_id`
- **KPI-снимки** — строятся поверх уже кэшированных `employees_comparison` и `users_summary`, сами по себе не дёргают Bitrix
